### 2.2 新业务链路

1. `frontend/src/App.tsx` 上传视频；`api.ts` 在 `VITE_BACKEND=spring` 时调用 `businessApi.ts`。
2. `POST /api/tasks` 由 `QueryController` 转到 `TaskService.upload()`：复制文件，在同一数据库事务内创建 QUEUED 任务、Outbox 和日志，并尝试写 Redis；返回 202。
3. `OutboxDispatcher` 每轮结束后延迟 2 秒再扫描待投递记录，`TaskPublisher` 等待 RabbitMQ confirm，成功后标为 sent。队列中仅有 taskId/videoPath。
4. `worker/consumer.py` 消费消息，通过内部 claim 取得 leaseToken 和服务器提供的输入路径；用 spawn 子进程执行 `pipeline_adapter.execute()`。
5. 子进程调用 `pipeline.run_video()`：YOLO + BoT-SORT → 公鹿识别锁定 → 规则触发 → 保存前后片段 → REVIEWING 回调 → 每个候选片段转码及 Qwen 复核 → 完整视频转码。
6. 父进程维持 AMQP 心跳并约每 2 秒调用内部 progress 续租；最后 POST events、PATCH COMPLETED，均成功后 ACK。
7. React 约每 2 秒刷新任务，终态停止对应轮询；Nginx 提供前端与视频，Spring 提供查询。

旧链路是 FastAPI + 进程内 `queue.Queue` + JSON/SQLite，不具备新队列的持久化机制。`run_video.py` 仍可以直接运行算法。新版通过注入 `ArchiveCollector` 绕开旧 SQLite 写入，但仍会导入 repository 模块，GPU Python 依赖暂未完全精简。

### 2.3 检测含义

- 公鹿识别目前依赖分类模型中的 `clothed_visible` 类及多帧概率累计，不等同于完整的公母鹿身份管理。
- `male_near`、`male_overlap`、`any_pair_iou` 是候选触发规则，不是骑跨、闻嗅等行为类别。`any_pair_iou` 的左侧目标也不保证是公鹿，写入 `male_track_id` 的语义应进一步明确。
- Qwen 按候选片段调用，默认以 1 FPS 读取视频；“疑似异常”被归一化为“异常”。模型给出的 confidence 不是经过校准的检测准确率。
- 无候选事件时不运行 Qwen。pipeline 汇总仍返回“正常/0.8”，React 用“未复核”覆盖显示，后端汇总语义尚未统一。

### 3.1 API 范围

现有公开接口：`POST /api/tasks`；`GET /api/tasks`、`/api/tasks/{id}`、`/api/tasks/{id}/progress`、`/api/tasks/{id}/events`；`GET /api/events`、`/api/events/{id}`；`GET /api/statistics/overview`、`daily`、`event-types`。

现有内部接口均在 `/api/internal/tasks/{id}` 下：POST claim、POST events、POST release、PATCH progress、PATCH status。事件详情路径中的 id 是数值主键，不是 eventId UUID。目前没有任务取消、人工重试、任务日志查询、输入文件下载或结果文件上传接口。

### 3.2 重试与归档需要明确的约定

当前事件事务提交后、完成事务提交前，事件已经能被列表和统计查询。若随后失败并重算，eventIndex 相同的旧记录不会更新，重跑新增的尾部事件还可能叠加。联合唯一键解决了“多插一行”，没有解决“本轮完整结果应该是哪一组”。

建议后续采用一个完成接口：先上传并验证本轮媒体，再在一个 MySQL 事务中校验当前租约、写入这一轮事件全集、任务汇总和 COMPLETED；事务成功后 Worker 才 ACK。未提交轮次不进入默认历史统计。保留唯一约束，重复完成请求返回已提交结果；ACK 丢失后仅重读终态，不重新推理。无需新增完整工作流引擎。

### 5.3 部署依赖与待补项

- Windows：Node/npm、JDK 17、Maven；基础设施可选 Docker Desktop/WSL2。保留一种文档主路径，避免要求所有开发者本地安装 GPU。
- Linux CPU：JRE 17 或业务镜像、Nginx、MySQL/Redis/RabbitMQ、持久卷；当前 Compose 镜像是 MySQL 8.4、Redis 7.4、RabbitMQ 3.13，历史记录 MySQL 是 8.0.46，应确定并验证一个目标版本，不直接升级现有数据卷。
- AutoDL：Python 3.10/3.11（pyproject 限制 <3.12）、与驱动匹配的 PyTorch/CUDA、Ultralytics、Transformers/Accelerate/qwen-vl-utils、OpenCV、ffmpeg/libx264、pika/requests、模型文件。PyTorch/CUDA 安装组合目前未锁定。
- 当前 `deploy/nginx_business.conf` 写死 `/root/autodl-tmp` 日志路径、`/var/www` 前端、`/var/lib` 媒体；业务启动脚本为 Bash，且 JVM 内存固定，缺 Windows 对应入口与环境区分。
- 原生 Rabbit 配置设置 12 小时 consumer_timeout，但 Compose 没有挂载它；长任务下两种部署的 ACK 超时行为不一致。需要统一配置并保留 Worker 自身执行时限。
- 原生初始化脚本需要 root/预装服务，不适合当作任意已有服务器的通用安装器；Redis 未认证 ping 不能可靠判断受密码保护实例是否已就绪，已有账号密码也不自动同步。
- `.env` 同时放业务库、Redis、MQ 和内部 token；GPU 节点只需要 MQ、内部 API 和模型配置，不应复制数据库凭据。

### 6.1 保留当前根目录布局

当前已经是 Monorepo 雏形。第一阶段保留目录名称，减少路径迁移风险；先统一职责、配置和发布入口。

  src/deer_behavior/           # 原 AI 核心与兼容入口
  configs/                    # AI 示例配置，不放真实权重
  deploy/
    local/                    # 后续：开发基础设施配置
    linux/                    # 后续：CPU 部署模板和进程管理
    autodl/                   # 后续：GPU 环境和托管模板

```

媒体、数据库卷、日志、Worker 缓存和模型放仓库外，并分别设置目录；只提交示例配置、构建文件和测试素材。不增加 Kubernetes、独立配置中心或额外编排服务。

### 6.2 Windows 本地开发

推荐模式：Windows 原生 React/Vite + Java 开发，WSL2/Docker 提供 MySQL/Redis/RabbitMQ；GPU 检测使用 AutoDL。全 Linux 工具链偏好者可以在 WSL2 启动业务模块。

建议开发端口保持 Vite 5173、Spring 6020、MySQL 3306、Redis 6379、RabbitMQ 5672/Management 15672。原生 AutoDL 6380 是已有部署选择，必须通过配置明确区分，不让文档混用。后端媒体根目录使用 Windows 可写绝对路径或 WSL 路径，AutoDL 使用自己的缓存目录，二者无需相同。

最小启动顺序：基础设施就绪 → Spring 连接成功并声明队列 → business 模式前端 → 可达内部 API/MQ 的 Worker。开发者可仅连接部署好的业务 API；不必本机安装 AI 权重。现有 integration-test-double 只允许隔离验收环境，正式任务必须使用真实推理。

### 6.3 CPU/GPU 分离部署

```text
Windows 浏览器/开发工具
       │ HTTPS 或本地端口转发
       ▼
Linux CPU 业务服务器
  Nginx + React + Spring Boot
  MySQL + Redis + RabbitMQ
  持久媒体目录（原视频、确认发布的结果）
       ▲                 │
       │ 内部 API/文件传输 │ MQ 任务
       └──── 私有通道 ────┘
                  AutoDL GPU Worker
                  本地输入缓存、模型、临时结果
```

最小方案选择“CPU 服务器保存权威文件 + Worker 经受保护内部接口下载/上传”，暂不引入对象存储或远程共享文件系统。现有绝对路径协议保留为同机兼容方式，新跨机方式以 taskId/逻辑文件标识寻址。

计划新增内部输入下载与产物上传接口，具体路径在 M03 固定：下载支持流式/Range；上传绑定任务和当前租约，只允许约定的产物标识，禁止任意绝对目标路径。Worker 下载至 `.part`、校验后改名；输出上传完成并通过验证后，Spring 返回可归档的服务器端文件引用。JSON 中的 clipPath/resultVideoPath 暂可继续用 CPU 端返回路径，以减少已有改动，不能再提交 GPU 本机路径。

API/MQ 通过 AutoDL 主动建立的 SSH 隧道或已有受控私网连接 CPU。可以分别转发 CPU 回环上的 6020/5672，避免公开数据库、Redis和内部接口；用户访问 6010 的通道与 Worker 通道独立。当前 Nginx 公共入口禁止 `/api/internal/`，GPU 应走独立内部通道。隧道端口、连接方向、服务恢复方式须写进部署手册。

运行权限：CPU Spring 只读写业务媒体，Nginx 只读媒体；GPU 只有内部 token/MQ 最小权限和本地模型/缓存权限。数据库和 Redis 不对 GPU 开放。初期单业务实例、单 GPU Worker，MQ 可积压，后续确有需求再扩容。

### 2.2 新业务链路

1. `frontend/src/App.tsx` 上传视频；`api.ts` 在 `VITE_BACKEND=spring` 时调用 `businessApi.ts`。
2. `POST /api/tasks` 由 `QueryController` 转到 `TaskService.upload()`：复制文件，在同一数据库事务内创建 QUEUED 任务、Outbox 和日志，并尝试写 Redis；返回 202。
3. `OutboxDispatcher` 每轮结束后延迟 2 秒再扫描待投递记录，`TaskPublisher` 等待 RabbitMQ confirm，成功后标为 sent。队列中仅有 taskId/videoPath。
4. `worker/consumer.py` 消费消息，通过内部 claim 取得 leaseToken 和服务器提供的输入路径；用 spawn 子进程执行 `pipeline_adapter.execute()`。
5. 子进程调用 `pipeline.run_video()`：YOLO + BoT-SORT → 公鹿识别锁定 → 规则触发 → 保存前后片段 → REVIEWING 回调 → 每个候选片段转码及 Qwen 复核 → 完整视频转码。
6. 父进程维持 AMQP 心跳并约每 2 秒调用内部 progress 续租；最后 POST events、PATCH COMPLETED，均成功后 ACK。
7. React 约每 2 秒刷新任务，终态停止对应轮询；Nginx 提供前端与视频，Spring 提供查询。

旧链路是 FastAPI + 进程内 `queue.Queue` + JSON/SQLite，不具备新队列的持久化机制。`run_video.py` 仍可以直接运行算法。新版通过注入 `ArchiveCollector` 绕开旧 SQLite 写入，但仍会导入 repository 模块，GPU Python 依赖暂未完全精简。

### 2.3 检测含义

- 公鹿识别目前依赖分类模型中的 `clothed_visible` 类及多帧概率累计，不等同于完整的公母鹿身份管理。
- `male_near`、`male_overlap`、`any_pair_iou` 是候选触发规则，不是骑跨、闻嗅等行为类别。`any_pair_iou` 的左侧目标也不保证是公鹿，写入 `male_track_id` 的语义应进一步明确。
- Qwen 按候选片段调用，默认以 1 FPS 读取视频；“疑似异常”被归一化为“异常”。模型给出的 confidence 不是经过校准的检测准确率。
- 无候选事件时不运行 Qwen。pipeline 汇总仍返回“正常/0.8”，React 用“未复核”覆盖显示，后端汇总语义尚未统一。

### 3.1 API 范围

现有公开接口：`POST /api/tasks`；`GET /api/tasks`、`/api/tasks/{id}`、`/api/tasks/{id}/progress`、`/api/tasks/{id}/events`；`GET /api/events`、`/api/events/{id}`；`GET /api/statistics/overview`、`daily`、`event-types`。

现有内部接口均在 `/api/internal/tasks/{id}` 下：POST claim、POST events、POST release、PATCH progress、PATCH status。事件详情路径中的 id 是数值主键，不是 eventId UUID。目前没有任务取消、人工重试、任务日志查询、输入文件下载或结果文件上传接口。

### 3.2 重试与归档需要明确的约定

当前事件事务提交后、完成事务提交前，事件已经能被列表和统计查询。若随后失败并重算，eventIndex 相同的旧记录不会更新，重跑新增的尾部事件还可能叠加。联合唯一键解决了“多插一行”，没有解决“本轮完整结果应该是哪一组”。

建议后续采用一个完成接口：先上传并验证本轮媒体，再在一个 MySQL 事务中校验当前租约、写入这一轮事件全集、任务汇总和 COMPLETED；事务成功后 Worker 才 ACK。未提交轮次不进入默认历史统计。保留唯一约束，重复完成请求返回已提交结果；ACK 丢失后仅重读终态，不重新推理。无需新增完整工作流引擎。

- AutoDL：Python 3.10/3.11（pyproject 限制 <3.12）、与驱动匹配的 PyTorch/CUDA、Ultralytics、Transformers/Accelerate/qwen-vl-utils、OpenCV、ffmpeg/libx264、pika/requests、模型文件。PyTorch/CUDA 安装组合目前未锁定。
- 当前 `deploy/nginx_business.conf` 写死 `/root/autodl-tmp` 日志路径、`/var/www` 前端、`/var/lib` 媒体；业务启动脚本为 Bash，且 JVM 内存固定，缺 Windows 对应入口与环境区分。
- 原生 Rabbit 配置设置 12 小时 consumer_timeout，但 Compose 没有挂载它；长任务下两种部署的 ACK 超时行为不一致。需要统一配置并保留 Worker 自身执行时限。
- 原生初始化脚本需要 root/预装服务，不适合当作任意已有服务器的通用安装器；Redis 未认证 ping 不能可靠判断受密码保护实例是否已就绪，已有账号密码也不自动同步。
- `.env` 同时放业务库、Redis、MQ 和内部 token；GPU 节点只需要 MQ、内部 API 和模型配置，不应复制数据库凭据。

## 6. 建议的 Monorepo 与环境

### 6.1 保留当前根目录布局

当前已经是 Monorepo 雏形。第一阶段保留目录名称，减少路径迁移风险；先统一职责、配置和发布入口。

```text
temporal_agent/
  frontend/                    # React 主前端，business 为推荐入口
  backend/                     # Spring 业务模块，后续放 SQL 迁移
  worker/                      # 队列消费、任务监督、文件传输适配
  src/deer_behavior/           # 原 AI 核心与兼容入口
  configs/                    # AI 示例配置，不放真实权重
  deploy/
    local/                    # 后续：开发基础设施配置
    linux/                    # 后续：CPU 部署模板和进程管理
    autodl/                   # 后续：GPU 环境和托管模板
  scripts/
    dev/                      # 后续：Windows/WSL 启动和检查
    deploy/                   # 后续：发布、回滚、备份
  docs/
    api/                      # 后续：接口与状态/事件字段约定
  .github/workflows/          # 后续：构建、验收、发布
  docker-compose.yml          # 保留当前基础设施入口，逐步调整
  .env.example                # 后续拆分开发/业务/Worker 示例
```

媒体、数据库卷、日志、Worker 缓存和模型放仓库外，并分别设置目录；只提交示例配置、构建文件和测试素材。不增加 Kubernetes、独立配置中心或额外编排服务。

### 6.2 Windows 本地开发

推荐模式：Windows 原生 React/Vite + Java 开发，WSL2/Docker 提供 MySQL/Redis/RabbitMQ；GPU 检测使用 AutoDL。全 Linux 工具链偏好者可以在 WSL2 启动业务模块。

建议开发端口保持 Vite 5173、Spring 6020、MySQL 3306、Redis 6379、RabbitMQ 5672/Management 15672。原生 AutoDL 6380 是已有部署选择，必须通过配置明确区分，不让文档混用。后端媒体根目录使用 Windows 可写绝对路径或 WSL 路径，AutoDL 使用自己的缓存目录，二者无需相同。

最小启动顺序：基础设施就绪 → Spring 连接成功并声明队列 → business 模式前端 → 可达内部 API/MQ 的 Worker。开发者可仅连接部署好的业务 API；不必本机安装 AI 权重。现有 integration-test-double 只允许隔离验收环境，正式任务必须使用真实推理。

### 6.3 CPU/GPU 分离部署

```text
Windows 浏览器/开发工具
       │ HTTPS 或本地端口转发
       ▼
Linux CPU 业务服务器
  Nginx + React + Spring Boot
  MySQL + Redis + RabbitMQ
  持久媒体目录（原视频、确认发布的结果）
       ▲                 │
       │ 内部 API/文件传输 │ MQ 任务
       └──── 私有通道 ────┘
                  AutoDL GPU Worker
                  本地输入缓存、模型、临时结果
```

最小方案选择“CPU 服务器保存权威文件 + Worker 经受保护内部接口下载/上传”，暂不引入对象存储或远程共享文件系统。现有绝对路径协议保留为同机兼容方式，新跨机方式以 taskId/逻辑文件标识寻址。

计划新增内部输入下载与产物上传接口，具体路径在 M03 固定：下载支持流式/Range；上传绑定任务和当前租约，只允许约定的产物标识，禁止任意绝对目标路径。Worker 下载至 `.part`、校验后改名；输出上传完成并通过验证后，Spring 返回可归档的服务器端文件引用。JSON 中的 clipPath/resultVideoPath 暂可继续用 CPU 端返回路径，以减少已有改动，不能再提交 GPU 本机路径。

API/MQ 通过 AutoDL 主动建立的 SSH 隧道或已有受控私网连接 CPU。可以分别转发 CPU 回环上的 6020/5672，避免公开数据库、Redis和内部接口；用户访问 6010 的通道与 Worker 通道独立。当前 Nginx 公共入口禁止 `/api/internal/`，GPU 应走独立内部通道。隧道端口、连接方向、服务恢复方式须写进部署手册。

运行权限：CPU Spring 只读写业务媒体，Nginx 只读媒体；GPU 只有内部 token/MQ 最小权限和本地模型/缓存权限。数据库和 Redis 不对 GPU 开放。初期单业务实例、单 GPU Worker，MQ 可积压，后续确有需求再扩容。
